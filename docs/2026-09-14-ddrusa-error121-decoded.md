# ddrusa ERROR 121 (3) decoded: the game never identifies the cassette

**Date:** 2026-09-14
**Screen:** `ERROR 121 / Cassette error. (3) / Cassette does not match this game. /
Check if the cassette is for this game (G*A44UAA)`
**Status:** the error's MEANING is now established from the game's own code. The
remaining question is narrow and named at the bottom.

## The error comes from PSX.EXE, not GAME.DAT

The on-screen text is mixed case. `GAME.DAT`'s string table is all-caps
(`SECURITY-CASSETTE ERROR (-11N)`, `=INCORRECT SECURITY CASSETTE=`). The mixed-case
message lives in `/PSX.EXE` (368,640 B, disc LBA 8216, loads at `0x80300000`):

    0x8033df84  "Cassette error. (%d1)\nCassette does not match this game.\n
                 Check if the cassette is for this\ngame (%s2)\n..."

That matches the hardware trace exactly: CD reads stop at LBA 8306, inside
PSX.EXE's extent (8216..8396). The disc loads the installer, the installer
rejects the cassette, and the install never starts -- which is why deleting
`ddrusa.sav` changed nothing.

Message table at `0x8034011c`, 12-byte entries `{english, japanese, 0}`, indexed
BY ERROR NUMBER: entry 120 = "Cassette is not installed", entry 121 = the above.
Exactly one site loads 121: `0x8030adf8`.

## What sub-code (3) means

`0x8030adc8` calls the verifier `0x80312e38`; a negative return goes through the
mapper `0x8030c15c`, which is a plain table:

| verifier returns | displayed |
|---|---|
| -12 | 1 |
| -1  | 2 |
| **-2 or -10** | **3** |
| -3  | 4 |
| -11 | 5 |
| -105 / -102 / -101 | 7 / 8 / 9 |

The verifier's first instruction is `addiu v1,zero,-0x2` -- **-2 is its default
return** -- and it then dispatches on a cassette TYPE word at `0x803f9640`:

    type == 1 or 2  -> X76 verify (0x8031397c)
    type == 3       -> ZS01 verify (0x80313a8c)
    anything else   -> falls through, returns the default -2

So **`(3)` means the game never identified the cassette at all.** It is not a
key, cipher, CRC or data mismatch -- the ZS01 verification path is never entered,
which is why the fabric sees `pkts=0` and `i2c_starts=0`.

## Where the type comes from

    0x80312d78  init: memset(state, 0, 0x74); type = 0x80323590(); store at 0x803f9640
    0x80323590  if (0x80323718() == 0) return -12;  else return 0x80324200()
    0x80324200  v = 0x803250b8();            // detector A
                if (v == 0) v = 0x80323fb4(); // detector B
                return v                      // 0 if neither recognises anything

Detector A (`0x803250b8`) drives the latch at `0x1f6a0000` directly:

    clear bit1 (SCL low) -> clear bits 1,2 (SCL low, CS low)
    -> clear bits 1,2,3 (SCL, CS, RST low) -> delay
    -> set bit3 (RST HIGH)  -> delay -> set bit1 (SCL high) -> ...

i.e. CS asserted, RST pulsed high, then SCL clocked while reading back. That is
the response-to-reset probe, and the fabric confirms we see it: `cs_seen=1`,
`rtr_probes=1`.

## Ruled out, each with evidence

* **Cassette image / type inference.** `max_byte=4115 -> latched type 2 (ZS01),
  selected 2 (ZS01)`. The staged `.u1` is 4116 B and matches the dump byte for
  byte (`tools/stage_zs01_u1.py --check`). The ZS01 IS the selected model.
* **The cipher.** `tb_zs01_golden` replays 13 golden wire vectors generated by an
  independent Python transcription of MAME (`tools/zs01_ref.py`) against the real
  ddrusa cassette; all 13 match byte for byte.
* **Engine latency / framing.** `OVERRUN=0`, and the game never sends a command
  anyway.
* **RTR content, bit order, edge and first-bit timing.** MAME's zs01 emits
  `5a 53 00 01` MSB-first on FALLING SCL, four bytes then STOP, and presents the
  first bit on the first falling edge (NOT at RST time) -- verified verbatim from
  `write_rst()` and the `STATE_RESPONSE_TO_RESET` arm. Our `zs01.v` does all of
  this identically. (The X76F041 being LSB-first is a genuine per-chip
  difference, not our bug.)
* **Disc/cassette mismatch.** ddrusa.iso's program identifies as `GN894EAA`
  (Euro Mix) -- but dsem.iso carries the IDENTICAL three `GN894` strings plus one
  `SIDENC`. It is inherited boilerplate from the engine DDR USA was built on, not
  a wrong disc.

## The remaining question

Detector A pulses RST (we see it) and then clocks SCL while reading the cassette
SDA back. It concludes "nothing here". So either it never clocks us, or it reads
the wrong line. The next measurements, in order of cheapness:

1. **How many RTR bits does the game actually clock out of us?** One saturating
   counter on falling SCL edges while `state == ST_RTR`. Zero means it never
   clocks the ID and the problem is upstream of the RTR entirely; 32 means it
   read our ID and rejected it, which moves the search to the read-back path.
2. **Where detector A reads SDA from, and what we present there.** It uses a
   `0x1f400000` base. `docs/MEMORY_MAP.md` labels `0x1f400006` bit 2 "Security
   cart IO0 tristate state" -- confirm against MAME's `k573cass` whether that
   bit is the SDA LEVEL, the wired-AND of device and latch, or a
   driven/tristated indication, and check what `s573_io.v` actually puts there.
   For the ZS01 the host drives SDA from CONTROL bit 6 rather than latch D0, so
   this read-back path is the one piece of the ZS01 wiring never yet measured.

Note both ZS01 benches clock the RTR the same way the RTL emits it, so neither
can detect a read-back-path error. That shared-assumption pattern has now caused
four wrong conclusions on this chip; measurement 1 exists to break it.
