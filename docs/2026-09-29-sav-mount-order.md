# Switching titles broke the next title's flash — the launcher mounted its .sav too late

**2026-09-29.** Root cause from the Main source, the RTL and the service log; reproduced in
simulation against the real saver (`sim/tb_s573_sav_mount_order.v`, red/green). Fix: launcher
order only — no FPGA build, no firmware change. Hardware: pending.

## The report

After ddr3mj played a full credit, every following launch misbehaved: ddr4mp's installer
stopped on ERROR 191 ("a different game is installed — G*A33J* DDR4thMIX must be installed
first"), ddr4mj and ddr3mj failed boot checks and were re-installed, ddrextrm failed too and
after its re-install the song unlock was gone.

## What the evidence says

* **The saves were not overwritten by bad data.** Every `.sav` the MiSTer wrote carries its
  clockless 1980-01-01 stamp. Today's re-installed `ddrextrm.sav` is byte-identical to the
  09-28 cabinet-verified backup (`out/sav-backup/ddrextrm.sav.20260928-tknv-good`) in the whole
  flash, card and cassette regions; only four timekeeper blocks differ (the settings the
  re-install reset, including the unlock). `ddr4mp.sav` / `ddr4mps.sav` still hold the blank
  flash they were staged with — only their cassette/timekeeper blocks were ever written.
* **The restore read two files.** The service's CD trace hook sits in Main's SD block handler
  and logs slot 4 too (`disk=4`, 1 KB blocks). Every launch in `s573mp3.log` shows ONE restore,
  starting ~6.6 s after core load at ~3,390 blocks/s and ending ~21 s.
* **Slot 4 holds the wrong file for the first seconds.** `user_io_init()` calls
  `parse_config()` (`user_io.cpp:1503`), which mounts every `SC<n>` slot from its bookmark
  (`:982-1011`) — `config/System573.s4`, rewritten on every slot mount (`menu.cpp:2785`), i.e.
  the **previous** title's `.sav`. `mgl_parse()` runs after (`:1528`), then the `boot.rom`
  autoload (`:1620-1631`). The launchers mounted their own `.sav` as the FIFTH item; `.mgl`
  delays count from the end of the previous item (`menu.cpp:1209-1218`), so that mount came at
  1+1+1+2+3 ≥ 8 s.
* **The restore does not restart on a remount.** `emu.sv` arms it when the download settle hold
  (3 s after EVERY download, the `.cas`/`.u6` included) ends — ~6.6 s, matching the log — with
  whatever slot 4 holds. `s573_flash_saver` latches its block count at LOAD start and keeps going
  through a remount ("a second mount while this load runs is the normal case"); the remount's
  `flash_load_taken` clear is re-set by the still-busy saver the next cycle.

So the first ~1.4–2 s of every restore (~5–7 MB, the start of the onboard flash) came from the
previous title's `.sav`. Relaunching the SAME title reads one file twice — harmless — which is
why this never showed until titles were switched back to back:

| launch   | bookmark (read first)  | result                                   |
|----------|------------------------|------------------------------------------|
| ddr4mp   | ddr3mj.sav             | ERROR 191 "a different game is installed" |
| ddr4mj   | ddr4mp/ddr4mps (blank) | boot checks failed → re-install          |
| ddr3mj   | ddr4mj.sav             | load failures → re-install               |
| ddrextrm | ddr3mj.sav             | failures → re-install, settings reset    |

A smaller `.sav` as the bookmark also latches a shorter block count, which can leave the tail
of the timekeeper region unrestored.

## The fix: the .sav is the first item

`<file delay="1" type="s" index="4" path="<rom>.sav"/>` now leads every launcher. It is then
mounted before the `.u1` download, whose `seceep_download` is a `saver_reset` term and re-arms
the load — so any restore begun from the bookmark is aborted, and the one that completes starts
after the last download settles, with the right file in the slot. Same six items, same set.

* `tools/stage_573.py` generates it (with the reason in the launcher's header comment).
* All 53 launchers with a slot-4 item were fixed — 18 regenerated by the stager (only the order
  and comment changed), the rest (ddrs2k, ddrusa, dsem, ddrsbm, hypbbc2p, konam80s and the 28
  superseded install/console pairs) by moving the one line. Deployed to `E:\_Console`,
  read back byte-identical; repo `mgl/` + `mgl/_superseded/` match; the previous card copies
  are in `local/mgl-backup-20260929-card/`. hyperbbc/gchgchmp have no slot 4 — untouched.

## Proof (`sim/tb_s573_sav_mount_order.v`)

The real `s573_flash_saver`; the emu.sv arm/settle/reset/clamp logic copied verbatim (constants
scaled); a Main model that mounts the bookmark at core init, autoloads `boot.rom`, runs the
`.mgl` items with cumulative delays and serves each slot-4 block from whatever file is mounted
at that moment; the per-block time set so a restore takes the logged 14.5 s.

* S1 shipped order, other bookmark → **6 of 48 blocks from the previous title** (the defect,
  ~1.8 s of 14.5 — as logged).
* S2 new order, other bookmark → image == own `.sav`, every block.
* S3 new order, no `boot.rom` (a restore from the bookmark starts at t0 and must be aborted by
  the `.u1`) → clean.
* S4/S5 same bookmark, either order → clean (why relaunching always worked).
* Every scenario: no SAVE during launch (neither file written), CPU released at the end.
* `make MGL_SAV_LAST=1 s573_sav_mount_order` (the old order in S2/S3) → RED, 2 failures.
  Default → GREEN. Neighbours `s573_flash_saver`, `_card`, `s573_tk_nv` still pass.

## ddr4mp / ddr4mps: ERROR 191 is the PLUS upgrade check

MAME gives exactly these two sets an `m48t58` region (`gca34ja.22h` / `gca34jb.22h`): an 8 KB
timekeeper image whose only content is the stamp `GCA33……JA` / `JB` + a checksum — "DDR 4thMIX
is installed", which is what the installer's message asks for. Every other title's timekeeper
starts with the installed game's ID the same way (`G*A33…JAA` ddr4mj, `GN887…JAA` ddr3mj,
`G*C36…JAA` ddrextrm). The launchers cannot carry an index-3 item (six-item cap), so the stamp
was written into the `.sav`'s timekeeper image (region block 2..9; `s573_tk_nv` applies it on
LOAD when the header matches, which it does), keeping each file's own clock bytes 8184..8191
(on this MiSTer `restore_clock` is 1 — Main reports 1970 — and MAME's zeros there would give the
RTC a date 0 / month 0). Only region block 2 changed in each file.

Caveat, from the same source: MAME marks ddr4mp and ddr4mps `MACHINE_NOT_WORKING`, and their
game-cassette dumps are `BAD_DUMP` 0x8c-byte images, not ZS01 images; the staged `.u1` is the
stager's 4116-byte pad. Getting past ERROR 191 does not guarantee the security check passes.
